# 인수 테스트 만들기

입력: 스토리 ID `$ARGUMENTS`

목적은 리팩터링 전에 지금 동작을 고정하는 것이다. 테스트가 말하는 것은 "지금 이렇게 동작한다"이지 "이렇게 바뀌어야 한다"가 아니다. 판단이 헷갈리면 이 목적으로 돌아간다.

## 1. 입력과 근거

- ID가 없거나 스토리 인덱스에 없으면 멈추고 묻는다. 스토리를 대신 고르지 않는다.
- `src/test/resources/features/<ID>.feature`가 이미 있으면 빠진 조건만 다룬다.
- 스토리와 거기 연결된 안건, 모순, 분석 문서, 주요 코드, 초기 데이터를 읽는다.
- 문서와 코드가 다르면 테스트를 쓰지 말고 묻는다. 코드에는 있는데 스토리에 없는 동작은 문서 문제로 알리고 조건에는 넣지 않는다.

## 2. 인수 조건

스토리의 현재 규칙을 사용자가 겪는 결과로 확인할 수 있는 조건으로 바꾼다. 기대값은 초기 데이터의 구체적인 값으로 잡는다.

고정하지 않는 것:

| 대상                              | 이유                                  |
| --------------------------------- | ------------------------------------- |
| 안건이나 모순에 걸린 동작         | 바뀔 수 있는 동작이다                 |
| "확인 필요"인 동작                | 기대값을 짐작하게 된다                |
| 스토리가 말하지 않는 것 (순서 등) | 우연히 그런 것을 규칙으로 만들게 된다 |
| "기능이 없다"는 규칙              | 사용자 흐름으로 확인할 수 없다        |

여기서 멈추고 아래 형식으로 승인을 받는다.

```
US-xx 인수 조건

포함
1. <조건> (근거: 스토리의 규칙)

제외
- <동작>: <이유>
```

## 3. 작성

- `src/test/java/gift/acceptance/AcceptanceTest.java`가 없으면 [references/cucumber-setup.md](references/cucumber-setup.md)대로 환경을 세운다.
- feature 파일은 비개발자가 읽는 문서다. `src/test/resources/features/<ID>.feature`에 두고, 첫 줄은 `# language: ko`, 기능 위에 `@<ID>` 태그를 붙인다. 인수 조건 하나가 시나리오 하나이고, 시나리오 이름은 조건 문장이다. 문장은 용어 사전의 말로 쓰고 경로, 상태 코드, 클래스명은 스텝 정의에만 둔다.
- 스텝 정의는 `gift.acceptance` 패키지에 도메인별로 둔다. 이미 있는 스텝과 방식을 먼저 찾아 따르고, 없으면 cucumber-setup.md의 예시를 따른다.
- 결과는 사용자가 받는 응답으로 확인하고, 프로덕션 클래스에 기대지 않는다. 그래야 리팩터링으로 깨지지 않는다.
- 시나리오마다 DB가 초기 데이터로 되돌아간다. 그래서 초기 데이터의 값과 개수에 기대도 되지만, 시나리오끼리 데이터를 주고받을 수는 없다. 한 시나리오에 필요한 데이터는 그 시나리오 안에서 만든다.

## 4. 확인

1. 테스트가 통과한다.
2. 실행된 시나리오 수가 작성한 수와 같다. 설정이 틀리면 0건으로 조용히 통과한다.
3. 기대값 하나를 일부러 틀려 실패하는지 보고, 되돌린 뒤 다시 통과하는지 본다.

## 5. 마무리

동작이 바뀌지 않으므로 보통 `docs/`는 그대로다. 1단계에서 찾은 문서 문제는 고칠지 묻고, 환경을 처음 세웠으면 CLAUDE.md 5장의 테스트 설명을 고친다.
