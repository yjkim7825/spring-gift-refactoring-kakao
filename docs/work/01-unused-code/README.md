# 1단계. 쓰이지 않는 코드 정리

[리팩터링 계획](../README.md)의 1단계 기록이다. 어디에서도 쓰지 않는 코드를 지웠다. 회원, 손님, 관리자가 겪는 동작은 바뀌지 않았다. 항목별 근거와 확인 결과는 [작업 목록](tasks.md)에 있다.

## 결과

| #   | 대상                                      | 결과                     | 남긴 것                                                  |
| --- | ----------------------------------------- | ------------------------ | -------------------------------------------------------- |
| D1  | 주문 처리에 연결만 해 두고 쓰지 않는 위시 | 안건 #4 결정 전까지 보류 | 그대로 둔다                                              |
| D2  | 주문 처리 설명 중 "위시 정리" 단계        | 안건 #4 결정 전까지 보류 | 그대로 둔다                                              |
| D3  | 주문에서 주문한 회원을 꺼내는 코드        | 지웠다                   | 주문에 회원을 기록하는 부분. 내 주문 내역을 찾을 때 쓴다 |
| D4  | 상품에서 옵션 목록을 꺼내는 코드          | 지웠다                   | 상품을 지우면 옵션도 함께 지우는 설정                    |

## 왜 이 단계를 먼저 했는가

### 동작이 바뀔 위험이 가장 적다

아무도 부르지 않는 코드는 지워도 결과가 달라질 수 없다. 쓰는 곳이 남아 있으면 프로그램이 만들어지지 않으므로, 실수하면 바로 드러난다. 그래서 리팩터링의 첫 단계로 삼아 테스트가 제대로 돌아가는지도 함께 확인했다.

### 이후 단계에서 손댈 양이 줄어든다

2단계에서 모양을 맞추거나 3단계에서 규칙을 옮길 때, 쓰지 않는 코드까지 함께 고칠 필요가 없다. 변경 내용에 꼭 필요한 줄만 남아 검토하기도 쉽다.

## D1, D2를 보류한 이유

처음에는 D1, D2도 지웠다가 점검하면서 되돌렸다.

쓰이지 않는 코드가 의도의 흔적일 수 있다. 주문 처리에 위시를 연결해 둔 것과 "위시 정리"라는 단계 설명은 주문 뒤 위시를 정리하려던 흔적으로 보인다. 이 설명은 [모순 M-2](../../contradictions.md#m-2-주문하면-위시에서-빠지는가)의 한쪽 근거이고, [안건 #4](../../agenda.md#고칠지-정할-동작)와 [주문 흐름 분석](../../order-flow.md#발견한-문제)의 O-9도 이 코드를 근거로 쓴다.

지우면 동작은 같지만, 안건 #4를 정하기 전에 "주문해도 위시를 정리하지 않는다" 쪽으로 모순을 정리한 것이 된다. 이것은 기획 판단이라 리팩터링에서 할 일이 아니다. 3단계에서 주문 규칙을 옮길 때도 위시 연결과 설명은 그대로 옮기고, 안건 #4가 정해질 때 함께 처리한다.

## 확인한 것

| 확인                | 결과                                              |
| ------------------- | ------------------------------------------------- |
| 인수 테스트 전체    | 변경 전과 후 모두 62개 통과, 시나리오 이름도 같음 |
| 지운 코드를 쓰는 곳 | 프로그램 코드, 테스트 코드, 관리자 화면에 없음    |
| 문서 점검           | 표 정렬 검사와 문체 검사 모두 통과                |

## 함께 고친 문서

동작이 바뀌지 않아 사용자 스토리와 용어 사전은 고치지 않았다. D3, D4를 근거로 쓴 문서도 없다. D1, D2를 되돌리면서 1단계에서 고쳤던 안건 #4 근거와 주문 흐름 분석 O-9 근거도 원래대로 돌렸다.

### 확인 방법

- 사용처 검색: `src/` 전체에서 `getMemberId`, `getOptions()`, `.options`를 찾았다. `src/main/resources/templates/`의 6개 파일에서 `memberId`, `options`, `getMemberId`, `getOptions`를 따로 찾았고 없었다. `Wish.getMemberId()`는 이름만 같고 다른 메서드라 그대로 두었다.
- JPA 영향: `Order`, `Product`는 `@Id`가 필드에 있어 필드 접근 방식이다. getter를 지워도 매핑과 파생 쿼리는 그대로다.
- 테스트: `gradlew test`가 `UP-TO-DATE`로 건너뛰어질 수 있어 `gradlew test --rerun`으로 실행했다. D3, D4만 남긴 상태에서 `tests="62" failures="0" errors="0" skipped="0"`이다.
- 문서 점검: CLAUDE.md의 `docs/*.md`는 하위 폴더를 포함하지 않아 `docs/work/` 아래 파일은 따로 넘겨 검사했다.
