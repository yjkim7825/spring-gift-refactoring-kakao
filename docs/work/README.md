# 리팩터링 계획

서비스 내부 코드를 일관된 구조로 정리하는 계획이다. 회원, 손님, 관리자가 겪는 동작은 바꾸지 않는다. 동작을 바꿔야 하는 것은 [안건](../agenda.md)에서 따로 정한다.

단계마다 이 폴더 아래에 작업 기록을 남긴다. 무엇을 했는지, 왜 그렇게 했는지, 어떻게 확인했는지를 적는다.

## 원칙

- 사용자가 보는 결과(성공과 실패, 안내 문구, 관리자 화면)는 리팩터링 전과 같아야 한다.
- 고치기 전에 그 기능의 인수 테스트가 있어야 한다. 없으면 먼저 만든다.
- 한 번에 한 종류의 변경만 한다. 정리, 모양 맞추기, 구조 바꾸기를 한 커밋에 섞지 않는다.

## 할 일

### 1. 쓰이지 않는 코드 정리

어디에서도 쓰지 않는 코드와, 하지 않는 일을 한다고 적힌 주석을 지운다. 지우기 전에 관리자 화면에서 쓰는지 다시 확인한다. 예를 들어 회원의 포인트를 꺼내는 코드는 프로그램 안에서는 쓰지 않지만 관리자 화면이 쓰고 있어서 지우면 안 된다. 안건이나 모순의 근거로 쓰이는 코드는 그 안건이 정해질 때까지 지우지 않는다.

| #   | 대상                                      | 이유                                                                    |
| --- | ----------------------------------------- | ----------------------------------------------------------------------- |
| D1  | 주문 처리에 연결만 해 두고 쓰지 않는 위시 | 안건 #4 결정 전까지 보류. 모순 M-2와 안건 #4의 근거다                   |
| D2  | 주문 처리 설명 중 "위시 정리" 단계        | 안건 #4 결정 전까지 보류. 모순 M-2의 한쪽 근거다                        |
| D3  | 주문에서 주문한 회원을 꺼내는 코드        | 어디에서도 쓰지 않는다                                                  |
| D4  | 상품에서 옵션 목록을 꺼내는 코드          | 어디에서도 쓰지 않는다. 상품을 지울 때 옵션도 함께 지우는 설정은 남긴다 |

### 2. 코드 모양 맞추기

같은 일을 곳마다 다르게 쓴 부분을 한 가지로 맞춘다. 동작에는 영향이 없다.

| #   | 다르게 쓴 부분                                                   | 맞추는 방향                                                                        |
| --- | ---------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| S1  | 부품을 연결하는 표시를 일부 파일에만 붙였다                      | 필요 없으므로 모두 뺀다                                                            |
| S2  | 변수 종류를 적는 방식이 세 가지로 섞여 있다                      | 변수의 종류를 직접 적는 방식으로 맞춘다                                            |
| S3  | 주소를 적는 방식이 두 가지로 섞여 있다                           | 짧은 쪽으로 맞춘다                                                                 |
| S4  | 목록을 만드는 방식이 한 곳만 다르다                              | 나머지와 같게 맞춘다                                                               |
| S5  | 응답 결과를 숫자로 적은 곳과 이름으로 적은 곳이 있다             | 이름으로 맞춘다                                                                    |
| S6  | 주문만 응답의 종류를 적지 않았다                                 | 다른 기능처럼 적는다                                                               |
| S7  | 파일 앞 설명 주석의 형식이 세 가지다                             | 이름만 되풀이하는 설명과 작성자 표시를 빼고, 규칙 설명은 문서 주석 형식으로 맞춘다 |
| S8  | 로그인 정보와 내용 형식을 알리는 이름을 글자로 직접 쓴 곳이 있다 | 미리 정의된 이름으로 맞춘다                                                        |
| S9  | 상품명 검사와 옵션명 검사를 부르는 코드가 똑같이 두 번 있다      | 3단계에서 한곳으로 옮긴다                                                          |

### 3. 규칙을 한곳으로 모으기

지금은 요청을 받는 곳에 업무 규칙이 모두 들어 있다. 예를 들어 "재고를 줄이고, 포인트를 빼고, 주문을 기록하고, 알림을 보낸다"는 주문 규칙이 요청을 받는 코드 안에 있다. 이 규칙을 기능별 처리 담당으로 옮긴다.

| 처리 담당 | 옮기는 규칙                                                                   |
| --------- | ----------------------------------------------------------------------------- |
| 카테고리  | 목록, 등록, 수정, 삭제                                                        |
| 상품      | 목록, 상세, 등록, 수정, 삭제, 상품명 검사, 카테고리 확인                      |
| 옵션      | 목록, 등록(같은 이름 막기), 삭제(마지막 옵션 지키기)                          |
| 위시      | 담기(이미 있으면 그대로 돌려주기), 목록, 빼기(내 위시인지 확인)               |
| 회원      | 회원가입, 로그인, 카카오 회원 찾기와 자동 가입, 관리자 회원 관리, 포인트 충전 |
| 주문      | 주문하기 전체 흐름, 내 주문 내역                                              |

의존이 적은 기능부터 옮긴다. 순서는 카테고리, 상품, 옵션, 위시, 회원, 주문이다.

주문 규칙을 옮길 때 위시 연결과 "위시 정리" 단계 설명(D1, D2)은 그대로 옮긴다. 안건 #4가 정해질 때까지 남겨 둔다.

옮기고 나면 로그인과 회원이 서로를 부르던 관계가 한 방향으로 정리된다. 지금은 회원 기능이 로그인 기능을 부르고, 로그인 기능도 회원 기능을 부른다. 그래서 한쪽을 고치면 다른 쪽도 함께 확인해야 한다.

### 4. 구조 규칙을 테스트로 고정하기

3단계에서 만든 구조가 다시 흐트러지지 않도록, 구조 규칙을 자동으로 검사하는 테스트를 만든다. 규칙을 어긴 코드가 들어오면 테스트가 실패한다.

- 요청을 받는 곳은 저장소를 직접 쓰지 않고 처리 담당을 거친다.
- 다른 기능의 저장소는 그 기능의 처리 담당을 거쳐서만 쓴다.
- 데이터 모양을 정의하는 코드는 요청을 받는 곳이나 요청, 응답 형식을 모른다.
- 처리 담당과 요청을 받는 곳은 정해진 이름 규칙을 따른다.
- 기능끼리 서로를 부르는 관계를 만들지 않는다. 상품과 옵션은 한 묶음이라서 예외로 둔다.

인수 테스트는 지금 US-01부터 US-05까지만 있다. 3단계에서 옵션, 위시, 주문, 관리 기능을 옮기기 전에 US-06부터 US-16까지의 테스트가 필요하다. 주문은 [주문 흐름 분석](../order-flow.md#리팩터링-전에-테스트로-고정할-동작)에 고정할 동작이 정리되어 있다.

## 이번에 하지 않는 것

사용자가 겪는 동작이 바뀌기 때문에 리팩터링에 넣지 않는다.

| 하지 않는 것                                  | 바뀌는 동작                                                                                        | 관련                                     |
| --------------------------------------------- | -------------------------------------------------------------------------------------------------- | ---------------------------------------- |
| 안내 문구의 언어 통일                         | 회원가입과 로그인은 영어, 상품과 옵션과 주문은 한국어로 안내한다. 맞추면 회원이 보는 문구가 바뀐다 | 정할 것                                  |
| 관리자 화면에서 없는 대상을 열 때의 처리 통일 | 관리자가 보는 오류 화면이 달라질 수 있다 (확인 필요)                                               |                                          |
| 오류 안내를 한곳에서 처리                     | 주문과 위시에서 "서버 오류"로 끝나던 경우가 "잘못된 요청"으로 바뀐다                               | [안건 #6](../agenda.md#고칠지-정할-동작) |
| 주문이 실패하면 모든 변경 되돌리기            | 실패한 주문의 재고와 포인트가 원래대로 돌아온다                                                    | [안건 #5](../agenda.md#고칠지-정할-동작) |
| 주문한 상품을 위시에서 빼기                   | 새로 생기는 동작이다                                                                               | [안건 #4](../agenda.md#고칠지-정할-동작) |

3단계를 마치면 안건 #5와 #6은 처리 담당 한곳만 고치면 되므로, 그때 따로 다루기 쉬워진다.

### 3단계 Service 구성

| Service           | 쓰는 곳                                                                                                      | 옮기는 Repository 사용 |
| ----------------- | ------------------------------------------------------------------------------------------------------------ | ---------------------- |
| `CategoryService` | `CategoryController`, `AdminProductController`, `ProductService`                                             | `CategoryRepository`   |
| `ProductService`  | `ProductController`, `AdminProductController`, `OptionService`, `WishService`                                | `ProductRepository`    |
| `OptionService`   | `OptionController`, `OrderService`                                                                           | `OptionRepository`     |
| `WishService`     | `WishController`                                                                                             | `WishRepository`       |
| `MemberService`   | `MemberController`, `AdminMemberController`, `KakaoAuthController`, `AuthenticationResolver`, `OrderService` | `MemberRepository`     |
| `OrderService`    | `OrderController`                                                                                            | `OrderRepository`      |

- 지금 컨트롤러는 `findById(...).orElse(null)`로 받아 `null`이면 `404`를 돌려준다. 동작을 유지하려고 Service는 `Optional`을 돌려주고, 컨트롤러가 지금처럼 `404`로 바꾼다.
- `IllegalArgumentException`을 받는 `@ExceptionHandler`는 지금 있는 컨트롤러(`MemberController`, `ProductController`, `OptionController`)에 그대로 둔다. Service에서 같은 예외를 던지면 응답이 같다.
- `@Transactional`은 붙이지 않는다. 붙이면 주문 실패 시 롤백되어 동작이 바뀐다(안건 #5).
- `auth`와 `member`의 순환은 `AuthenticationResolver`와 `KakaoAuthController`가 `MemberService`를 쓰고, `MemberController`가 `JwtProvider`를 쓰는 구조로 바뀐다. 방향을 한쪽으로 정하려면 `JwtProvider`와 `TokenResponse`의 위치도 함께 정해야 한다.

### 4단계 ArchUnit 규칙

`com.tngtech.archunit:archunit-junit5`를 `testImplementation`에 추가하고 `src/test/java/gift/architecture/`에 규칙을 둔다. 버전은 추가할 때 최신 안정판을 확인한다.

| 규칙                                                    | ArchUnit 표현                                                                                      |
| ------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| 컨트롤러는 Repository에 의존하지 않는다                 | `@Controller`, `@RestController` 클래스가 `JpaRepository` 하위 타입에 의존하지 않음                |
| 다른 도메인의 Repository는 그 도메인의 Service로만 쓴다 | `*Repository`는 같은 패키지의 클래스만 접근                                                        |
| 엔티티는 컨트롤러와 DTO에 의존하지 않는다               | `@Entity` 클래스가 `*Controller`, `*Request`, `*Response`에 의존하지 않음                          |
| 이름 규칙                                               | `@Service`는 `*Service`, `@Controller`와 `@RestController`는 `*Controller`로 끝남                  |
| 필드 주입 금지                                          | `@Autowired` 필드가 없음                                                                           |
| 도메인 사이 순환 금지                                   | `slices().matching("gift.(*)..").should().beFreeOfCycles()`, product와 option의 엔티티 연관은 예외 |
