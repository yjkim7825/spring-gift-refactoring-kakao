# 모순 목록

사용자 스토리와 주문 흐름을 정리하면서 찾은 모순이다. 여기서 모순은 서비스 안의 두 곳이 같은 대상에 대해 서로 다른 말을 하는 것을 뜻한다. 각 모순을 어느 쪽으로 정리할지는 [안건](agenda.md)에서 다룬다.

## M-1. 상품에는 옵션이 꼭 있어야 하는가

- 한쪽: 옵션을 삭제할 때는 "옵션이 하나뿐인 상품은 옵션을 삭제할 수 없다"는 규칙을 지킨다. 상품에는 옵션이 항상 하나 이상 있어야 한다는 뜻이다.
- 다른 쪽: 상품을 새로 등록할 때는 옵션을 만들지 않는다. 등록한 직후의 상품에는 옵션이 하나도 없다.
- 결과: 같은 규칙을 삭제할 때만 지키고 등록할 때는 지키지 않는다. 옵션이 없는 상품은 주문할 수 없다.

## M-2. 주문하면 위시에서 빠지는가

- 한쪽: 주문 처리 순서를 적어 둔 설명에는 "위시 정리" 단계가 있다.
- 다른 쪽: 실제로는 이 단계를 실행하지 않는다. 주문한 상품이 위시에 그대로 남는다.

## M-3. "카카오"가 들어간 상품명을 쓸 수 있는가

- 한쪽: 관리자 화면에서는 "카카오"가 들어간 상품명을 항상 허용한다.
- 다른 쪽: 화면 없이 등록하는 경로에서는 같은 상품명을 항상 거부한다.
- 결과: 규칙은 "담당 MD와 협의한 경우에만 허용"인데, 어느 쪽도 협의 여부를 확인하지 않는다. 등록하는 곳에 따라 결과만 다르다.

## M-4. 주문은 선물인가

- 한쪽: 서비스 이름은 "선물하기"다. 알림은 "선물이 도착했어요!"로 시작하고 "선물 확인하기" 버튼이 있다. 주문 메시지도 "생일 축하해!"처럼 받는 사람에게 쓰는 말로 쓰인다.
- 다른 쪽: 주문에는 받는 사람이 없다. 알림은 카카오톡 "나에게 보내기"로 주문한 사람 자신에게 간다.

## M-5. 주문 메시지는 몇 자까지 쓸 수 있는가

- 한쪽: 주문할 때는 메시지 길이를 확인하지 않는다. 얼마든지 길게 써서 보낼 수 있다.
- 다른 쪽: 주문을 기록할 때는 255자까지만 저장할 수 있다.
- 결과: 255자를 넘는 메시지는 주문을 접수한 뒤 기록하는 단계에서야 실패한다. 그 사이에 재고와 포인트는 이미 빠진다(확인 필요).

## M-6. 로그인하지 않았을 때 어떤 안내를 받는가

- 한쪽: 로그인 정보가 틀리거나 만료되었으면 "로그인이 필요하다"고 안내한다.
- 다른 쪽: 로그인 정보를 아예 보내지 않았으면 "잘못된 요청"으로 안내한다(확인 필요).
- 결과: 둘 다 로그인하지 않은 같은 상황인데 안내가 다르다.

## M-7. 주문 하나를 따로 볼 수 있는가

- 한쪽: 주문이 끝나면 "이 주문은 이 주소에서 볼 수 있다"며 주문별 주소를 돌려준다.
- 다른 쪽: 그 주소로 주문을 보는 기능이 없다. 주문은 내역 목록으로만 볼 수 있다.

## M-8. 관리자 화면에서 비밀번호를 가리는가

- 한쪽: 회원 수정 화면의 비밀번호 칸은 입력한 글자를 가려서 보여 주는 칸이다.
- 다른 쪽: 그 칸에 회원의 실제 비밀번호를 미리 채워 둔다. 화면을 연 사람은 웹 페이지 원본에서 비밀번호를 그대로 볼 수 있다.

| #   | 한쪽                                                                                                                                | 다른 쪽                                                                                                      |
| --- | ----------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| M-1 | `OptionController.deleteOption`의 `options.size() <= 1` 검사, 클래스 주석 "Each product must have at least one option at all times" | `ProductController.createProduct`, `AdminProductController.create`가 옵션을 만들지 않는다                    |
| M-2 | `OrderController.createOrder` 주석 "6. cleanup wish"                                                                                | `wishRepository`를 주입만 하고 쓰지 않는다                                                                   |
| M-3 | `AdminProductController`가 `ProductNameValidator.validate(name, true)`를 호출한다                                                   | `ProductController.validateName`이 `ProductNameValidator.validate(name)`, 즉 `allowKakao = false`로 호출한다 |
| M-4 | `KakaoMessageClient.buildTemplate`의 문구 "🎁 선물이 도착했어요!", `button_title` "선물 확인하기"                                   | `Order`에 수신자 필드가 없다. `/v2/api/talk/memo/default/send`("나에게 보내기")를 쓴다                       |
| M-5 | `OrderRequest.message`에 `@Size`가 없다                                                                                             | `orders.message`가 `varchar(255)`다. `@Transactional`이 없어 앞 단계가 이미 커밋된다                         |
| M-6 | `AuthenticationResolver.extractMember`가 `null`을 돌려주면 `401`                                                                    | `@RequestHeader("Authorization")`가 필수라 헤더가 없으면 `400 MissingRequestHeaderException` 예상            |
| M-7 | `createOrder`가 `Location: /api/orders/{id}`를 돌려준다                                                                             | `GET /api/orders/{id}` 매핑이 없다                                                                           |
| M-8 | `templates/member/edit.html`의 `<input type="password">`                                                                            | 같은 입력의 `th:value="${member.password}"`. `Member.password`는 평문이다                                    |
